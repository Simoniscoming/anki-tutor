## 何时读

用户表露**想看自己的 Anki 表现 / 想优化复习**时（这是 description 的诊断触发条件）。典型：

- "看看我最近的 retention" / "我学得怎么样"
- "最近忘的多" / "retention 掉了"
- "复习太多扛不住" / "这牌组是不是失控"
- "哪些卡该删" / "哪些卡老记不住"

**被动响应，绝不轮询**。Skill 不是 daemon——用户不问就不拉 revlog。每次触发也只拉相关时间窗，不全库扫描。

---

## 读意图（诊断前置）

**采集数据前先读 `intent.json`**（见 [`./intent-persistence.md`](./intent-persistence.md)）：

- **有意图** → 后续诊断按该牌组的配方分支解释（见决策树第二步）
- **无意图** → 先明确告知用户：「未设目标，以下诊断倾向 FSRS 通用最优（≈ 配方 A），可能与你的实际诉求冲突——要不要先设个目标？」再继续

意图是诊断不「归一化」的根基。用户短期想提效拉高 DR，若无意图记录，诊断会单纯因「实际保留率低于 DR」而建议降 DR，毁掉用户的速通初衷。

## 采集

**一次 `multi` 调用拉齐**（见 [`./anki-control.md`](./anki-control.md) 模板9），减少 curl 往返：

| 数据 | action | 用途 |
|---|---|---|
| 当前 desiredRetention | `getDeckConfig` | 对比基准 |
| 各牌组 new/learn/review 计数 | `getDeckStats` | 看负载分布 |
| 某 deck 的复习记录 | `cardReviews`（按 deck + 时间窗） | 算保留率 |
| 每日复习量趋势 | `getNumCardsReviewedByDay` | 看连续性、量级 |

时间窗建议：默认看**近 30 天**（短期问题）；用户问“长期表现”再看近 90 天。

⚠ **比较基准是 DR，不是任何「最优保留率」**。FSRS Issue #694 显示 Anki 25.02 的「计算最低建议保留率」(CMRR) 按钮常返回 0.70、不可靠，且 AnkiConnect 读不到内置优化值。故本 Skill 一律以 `getDeckConfig` 读到的 desiredRetention 为比较基准，不以 CMRR 为据。

## 指标

### 1. 实际保留率（核心）

**只算 mature 卡的复习记录**——interval>21 天才算"真的记住了"，才有和 DR 比较的意义。新卡/学习中的卡不算。

- 从 `cardReviews` 返回里筛：`type==1`（复习记录），且该次 `ivl>21`
- `ease>=2` = 答对（`ease==1` = Again = 忘了）
- 实际保留率 = 答对数 / 总数
- 和 `desiredRetention` 比

⚠ revlog 是 **list 不是 dict**（9 字段：id/cid/usn/ease/ivl/lastIvl/factor/time/type）。**实测值**（2026-08 验证）：`type` 0=学习 / 1=复习 / 2=relearn；`ease` 是按钮 1=Again(忘) / 2=Hard / 3=Good / 4=Easy，答对 = `ease>=2`。仍建议首次打印一条记录核对——Anki 版本间可能有差异。

### 2. 单卡 lapses

从 `cardsInfo` 的 `lapses` 字段（这张卡累计忘了多少次）。

### 3. 负载比（辅助上下文，不单独触发建议）

复习量 / 新卡量。**无权威阈值**（社区数值多为个案）。它不单独触发任何决策树行，只作辅助上下文：在心理负荷行里判断「负载可接受」、在综合建议里定性描述负担趋势。持续上涨 + 用户感到不可持续 = 减负信号，但要和别的指标合看。

### 4. 复习连续性

`getNumCardsReviewedByDay` 看断卡天数。

## 聚合粒度——找"烧时间的概念"：按 note，不按 card

指标 #2 的 lapses 是**按卡**的。但判断"哪个**概念**复习成本高"时，按**笔记聚合**：把同一 note 的所有卡的 reps/lapses 加总，count 卡数。

为什么：Cloze 枚举笔记 = 1 个概念生成 N 张卡（每个删除项一张），N 卡各自被 FSRS 调度、各自攒 reps。按卡看会把一个枚举概念拆成 N 行，**低估**它的真实消耗（本库实测枚举概念比单卡概念多吃约六成 reps——你的库可能不同，别当普适常数）。

怎么聚合：`cardsInfo` 每张卡返回 `note` 字段 → 按 noteId group → sum reps、sum lapses、count cards。`cards>1` 的 note 标记为枚举候选。

⚠ 别和 leech 判定混：note 聚合找的是"**贵**"的概念（reps 高、lapses 低 = 反复刷且大多答对）；leech 判定**仍用单卡 lapses≥8**（指标 #2）。"贵"≠"烂"——贵的卡不该删，只该考虑降成本（见末尾「占位：卡片合并建议」）。

## 决策树

**先读意图，再判阈值**（意图读取见上方「读意图」）。阈值全是**经验值**，告诉用户这是启发式不是科学。

### 第 0 步：FSRS 是否启用（最高优先级，先于一切）

诊断的第一件事不是算保留率，而是确认用户**是否在用 FSRS**。还在 SM-2 的用户，切到 FSRS + 优化一次的收益 > 任何微调。没开 FSRS 时，下面所有诊断（保留率、配方、复习负担预测）都建立在 SM-2 调度上，意义打折。

**怎么检测**：

- **首选**：配套插件 fsrs_bridge 在运行（8766）→ 调 `fsrsStatus {"deck":牌组}`，直接拿到 `v3scheduler` + `fsrsEnabled` + `daysSinceLastOptimize`，最准
- **降级**（插件没装）：从 `getDeckConfig` 的 `fsrsParams6`/`fsrsWeights` 间接判断（非空 = FSRS 在用；null 要先排除"继承父级"——查父牌组 config）

**检测结果分支**：

| 状态 | 建议 |
|---|---|
| 未开 FSRS | **最高优先级**。插件在 → 路由到 [`./fsrs-optimize.md`](./fsrs-optimize.md) **场景 A**（主动提议帮开，fsrsSetEnabled，确认后执行）。插件没装 → 指引用户在 GUI 一次性开启 |
| 开了但从没优化过 / 距上次优化很久 | 读 `optimize-log.json` 或 fsrsStatus 的 `daysSinceLastOptimize` 判断。攒够数据（≥1000 条）→ 路由到 fsrs-optimize.md **场景 B** 优化 |

为什么这是第 0 步：FSRS 作者的设计前提就是"权重交给 Optimize"。一个没开 FSRS、或开了但从没优化的库，调 desiredRetention / 配方都是在次优解上打转。先把这层理顺，后面的诊断才有意义。

注：检测本身只读。**开启/优化是写操作，走 fsrs-optimize.md 的确认流程**（不在诊断里直接改）。

### 第一步：检测——三道闸（与意图无关，纯统计）

实际保留率长期偏低需**三道闸全过**才成立。FSRS 自身 RMSE≈1.5-2%（Issue #215），单看「实际 < DR−5 个百分点」会踩噪声边，故需幅度 + 样本 + 持续双重过滤：

| 闸门 | 条件 |
|---|---|
| 幅度 | 实际保留率 < DR − 5 个百分点 |
| 样本 | 窗口内 mature（interval>21 天）复习量 ≥ 200 |
| 持续 | 窗口跨度 ≥ 30 天 |

窗口起点 = max(intent.setAt, 今天−90 天)：刚改过 DR，跨改动的窗口无效；改动不足 30 天则「持续」闸自动不过，提示「观察期不足，≥30 天后再来」。三闸不全过 → 输出「样本/时间不足，暂不判断，继续观察」，不下结论。

### 第二步：解释——按配方分支（意图决定动作）

检测触发后，建议什么动作取决于该牌组的配方：

| 命中检测 + 配方 | 建议 |
|---|---|
| 实际偏低 **且 配方 A/D/E**（长期型） | 卡质差 **或** DR 设太高：抽样高频失败卡→拆细/删；或降 DR 2-3 个百分点（原逻辑，唯一该降 DR 的场景） |
| 实际偏低 **且 配方 C**（减压维护） | DR 已在 0.85-0.88 低位，**不再下调**（破 0.80 红线、FSRS <0.80 不可靠）。优先怀疑卡质：抽样高频失败卡→拆细/删；或减新卡。若同时 backlog 暴涨 / streak 断裂 → 判为状态问题，鼓励而非调参（社区共识：6 年用户"烂卡重做或删"） |
| 实际偏低 **且 配方 B + deadline 未到** | 速通的预期代价，**别降 DR**；考虑加复习预算或减新卡 |
| 实际偏低 **且 配方 B + deadline 已过** | B 不可持续已应验，**主动触发 B→A/C 迁移**（路由回 [`./recipes.md`](./recipes.md)） |
| 实际偏低 **但 intent.accepts 声明「低保留/高负载已接受」** | 压制归一化建议，只提示，不动 |
| 实际≈DR、负载可接受 **但 backlog（逾期）持续增长 或 用户表露刷得痛苦/想放弃** | 非效率问题，是**心理负荷/状态问题**（FSRS simulator 看不见的盲区）；降 DR 反而更糟。建议减新卡、清逾期、或切配方 C 维护期；状态差时鼓励 > 调参 |
| 单卡 lapses ≥ 8 | leech：删 / 重做 / 挂起（Anki 默认 leech 阈值=8） |
| 某牌组 review 占全库 >1/3 | 该牌组失控：分层 DR 或暂停加新 |
| streak 中断 | 状态问题，非技术：鼓励，不指责 |

**多重现象常并发**（如「实际低 + 负载高」= 卡质差又量大）。把所有命中一次列清，给综合建议，别只盯一行。

### 第三步：交叉校验防漂移

比较 `intent.currentDR` 与 Anki 实际 DR：不一致 → 提示「你曾设配方 X（DR Y），现为 Z，是手动改过吗？哪个是当前意图？」——抓住 GUI 手改 + 意图文件失同步。改任何配置都走 recipes.md 的预览+确认（同 SKILL.md 红线1）。

## 复习负担预测（未来负载预警）

决策树诊断的是**现状**（保留率掉没掉、有没有 leech）。这一节诊断的是**未来**：按用户当前的新卡量，几周后复习量会不会爆。它回答用户最常问的"我每天加这么多新卡，扛得住吗"。

### 为什么必须预测，不能看近期趋势

加新卡的当下，复习量几乎不变——**前 2 周曲线是平的**，用户误以为没问题。但每张新卡后续要反复复习，1-3 个月后会爆发。所以**必须用预测/外推，看近期复习量趋势会漏报**。

典型延迟曲线（社区高度一致的描述）：

| 阶段 | 时间 | 表现 |
|---|---|---|
| 潜伏期 | 0-2 周 | 复习量几乎不变（**用户误判安全**）|
| 爬坡期 | 2-8 周 | 新卡陆续毕业进复习队列，线性上升 |
| 爆发期 | 1-3 个月 | 快速翻倍接近峰值 |
| 稳态 | 6-18 个月 | 达到平台 |

### 核心比率：稳态复习/天 ≈ 新卡/天 × k

社区共识（基于多帖用户自报，非统计结论）：

| 算法 / 目标保留率 | k |
|---|---|
| SM-2 @ 90% | 9-10× |
| FSRS @ 90% | 8-10× |
| FSRS @ 85% | 6-7× |
| FSRS @ 80% | 5× |
| FSRS @ 95% | ~18×（高 retention 边际成本爆炸）|

口诀：**每天 N 张新卡 → 稳态约 N×10 复习/天**。注意高 retention 的代价：90%→95% 复习量 +88%，记住的量只 +2.7%。

### 三级预测方案

**方案 A（系数法，默认，零依赖）**——按上表 k 乘当前新卡量，得到稳态预测。最粗但即时可用。

```
forecast_steady = 当前新卡/天 × k(算法, desiredRetention)
预警：forecast_steady > 用户容量阈值
  容量默认：200 卡/天 或 45 分钟（按 sec/卡≈8s 估）
  用户可在意图/配方里自定义
```

**方案 B（历史比率外推，中等精度）**——用真实历史校准 k：

```
r = 近30天总复习 / 近30天总新卡（getNumCardsReviewedByDay + getDeckStats）
forecast = r × 当前新卡/天
```

⚠ 方案 B 在用户**刚加大量新卡时会严重低估**（延迟效应，新卡还没毕业进复习队列），必须用方案 A 的系数上限兜底——取 `max(A, B)`。

**方案 C（py-fsrs 逐卡重放，精确曲线，占位）**——从 `cardsInfo` 拿每张卡的 memory state，喂给 py-fsrs 逐日推进算未来 N 天的 due 数曲线，能给出"60 天后峰值 X"的精确预测。**当前不实现**，等决定是否引入 Python 依赖后回来做。

### Backlog（逾期）——"已经失控"的现时信号

预测看未来，backlog 看现在。两者配合：

```
backlog_days = 当前 due 数 / 近7天日均复习量
backlog_days > 7  → 黄色预警
backlog_days > 14 → 红色预警（社区普遍认为此时已难恢复）
backlog / 总复习量 > 0.5 → 危险
```

案例锚点（社区）：4000+ backlog 即"危机"；停卡 4 天 → 900 due，做掉 100 → 次日回到 340（复习债复利）。

### 触发与输出

复习负担预测和决策树并行跑，结果合并进下方「输出」的数据快照。预警条件（都报）：

1. `forecast_steady > 容量` → 长期不可持续
2. backlog_days > 7 → 当前已失控（不等未来）
3. 近 14 天新卡量明显上升 + forecast 斜率为正 → 早期信号（潜伏期就该提醒，别等爆发）

建议动作（路由回 recipes.md / 决策树）：

- 长期不可持续 → 降 desiredRetention（最有效的泄压阀，见 recipes.md 配方 C）或减新卡量
- 当前失控 → 切配方 C 维护期（暂停新卡，只清复习）
- 潜伏期早期信号 → 提前预警，让用户在爆发前调整

人群可持续新卡量参考见 recipes.md「人群每日新卡量参考」表。

## 输出

**只建议，不自动改**。每次诊断给三块：

1. **数据快照**：实际保留率 X% vs DR Y%、负载比、top leech 几张（带卡名/noteId）
2. **命中的诊断**：决策树里哪几行被触发
3. **2-3 个可选动作**，让用户选

要改配置（如降 DR）时，**路由回 [`./recipes.md`](./recipes.md) 的「应用」**——走预览+确认，不在诊断流程里直接改。

## 占位：卡片合并建议（未来，配合诊断看板，暂不实现）

**场景**：枚举型卡（Cloze 多空 / 一概念多子卡）复习成本高。当某枚举概念**已稳定**（成功率高 + 复习次数足够）时，可建议把多张子卡**合成 1 张**，省预算。

**触发 = 指标 ∧ 目标，两者都要**：
- 指标：成功率 ≥ ?、累计复习次数 ≥ ? —— **阈值待定，现在不定**
- 目标门槛：
  - 牌组目标是**维护/长期** → 倾向**建议合成**（稳定的东西不必逐项测，省预算）
  - 牌组目标是**冲刺/应试** → **不建议合成**（每项独立可召回更重要）

**为什么留占位不定阈值**：阈值必须和牌组目标绑定才有意义，拍脑袋定一个数会误判。等做"诊断看板"环节（有目标系统 + 可视化指标）再回来定。

**当前做法**：诊断时若发现"贵但稳定"的枚举概念，可口头提一句"这批可考虑合成"，但不自动建议、不给硬阈值。

## 红线

- **诊断全程只读**：只拉 revlog、给建议，不主动调 FSRS、不删卡、不挂起。
- 改任何配置都走 recipes.md 的确认流程（同 SKILL.md 红线1）。
- 删 leech / 挂起卡也要用户明确点头（呼应 SKILL.md：改卡操作要确认）。
- 阈值是经验值，别说成科学结论。用户的情况永远优先于决策树。
- **别和制卡抢活**：诊断发现"卡质差"时，建议用户回炉重拆，但具体拆卡走制卡主工作流（SKILL.md ①→⑦），不在本文件里重造。
